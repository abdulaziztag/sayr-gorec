# sayr-gorets

Сборщик сообщений форума «ГОРЕЦ» (@gorets_uzb) и недельный разбор ИИ для Sayr.

Раз в день забирает новые сообщения форума в свою базу Postgres, раз в неделю
разбирает прошедшую неделю моделью Claude и присылает владельцу отчёт в личку
Telegram: какие места в ходу и что о них говорят, каких мест нет в каталоге
Sayr, какие выходы объявлены, о чём чаще всего спрашивают, что говорят о Sayr.

Проект живёт рядом с сервером Sayr на том же VPS, но к его коду и базе не
обращается: своя база, своя роль, свой `.env`, свои таймеры systemd.

## Как это устроено

**Чтение.** Форум читается через MTProto библиотекой Telethon под обычным
аккаунтом Telegram: бот Bot API историю группы не видит, аккаунт-участник —
видит. Аккаунт задаётся строкой сессии в `.env`, код не зависит от того, чей
это аккаунт. Только чтение: в группу ничего не пишется, реакции не ставятся,
в другие чаты аккаунт не вступает. Единственное исходящее сообщение — отчёт
владельцу в личку.

**Бережно к лимитам.** Между запросами к Telegram пауза (по умолчанию
1,5 с), на FloodWait ждём столько, сколько сказано (до часа, настраивается);
большая догрузка истории идёт порциями с продолжением с места остановки.

**Сбор — раз в день** (таймер systemd, 04:00 по Ташкенту). По каждому чату из
настроек читаются сообщения с id больше последнего сохранённого и пишутся
upsert'ом по ключу `(chat_id, msg_id)` — повторный прогон ничего не
дублирует. Чат, которого в базе ещё нет (только что добавленный в
`GORETS_CHATS`), при первом сборе сканируется с даты `GORETS_INITIAL_SINCE`
(по умолчанию 1 января 2026); прерванное сканирование продолжается по id. В конце прогона удаляются сообщения старше срока хранения. Каждый
прогон записывается в журнал (`runs`): начало, конец, сколько новых,
последний id, ошибка. Ошибка — ненулевой код выхода, служба становится
`failed`, это видно в `systemctl --failed`.

**Разбор — раз в неделю** (понедельник, 09:00 по Ташкенту; неделя — с
понедельника по воскресенье по Ташкенту). Две ступени: куски недели →
Claude Message Batches API (вдвое дешевле обычных запросов), затем сведение
всех JSON одним обычным вызовом Messages API. Подробнее — в разделе
[Разбор недели](#разбор-недели).

## Выбор аккаунта Telegram и риски

Рекомендуется **отдельный аккаунт** на отдельном номере, вступивший в
«ГОРЕЦ». Он ничего не пишет и ничего не скачивает, но Telegram может
счесть массовое чтение истории подозрительным и ограничить аккаунт; на
отдельном аккаунте это ни на что больше не повлияет.

**«Sayr Admin» брать не советуем.** Это аккаунт, который заводит группы
комнат попутчиков (служба `sayr-tg` на том же сервере). Жалобы или
ограничение аккаунта за сбор данных уронят группы комнат. Если всё же
решено использовать его — только отдельным входом (своя сессия через
`gorets login`), **никогда не копируйте строку `SAYR_TG_SESSION`** в
`GORETS_TG_SESSION`: два клиента на одном ключе авторизации Telegram может
разорвать, и группы комнат перестанут создаваться.

**Антиспам для нового аккаунта.** Свежий аккаунт, первым написавший
незнакомому человеку, может попасть под ограничения. Поэтому владелец
сначала сам пишет аккаунту-сборщику (любое сообщение) или добавляет его в
контакты, и только потом включается таймер разбора. Отчёт уходит в этот
же диалог.

## Что хранится и сколько

База Postgres `sayr_gorets`, роль `sayr_gorets`, в том же Postgres, что у
сервера Sayr.

**Сообщение** (`messages`, ключ `chat_id` + `msg_id`): чат, id, дата
(timestamptz), ветка (id и название), «ответ на» (id), автор — только
HMAC-SHA256 от id пользователя с секретом из `.env` (простой хеш числового
id подбирается перебором, HMAC с секретом — нет), текст после очистки, тип
вложения (`photo`, `video`, `document`, `gpx`/`kml` по имени файла,
`voice`, `sticker`, `poll`, `location`, `venue`, `other`), имя файла
документа, координаты статичной точки или venue (округлены до трёх знаков,
около 100 м; живые геопозиции без координат), название канала при
пересылке (пересылки от людей — без источника), время правки, время сбора.

**Очистка текста при записи** (кроме веток фидов с `keep_contacts`, см.
[ниже](#фиды-извлекатели-и-api-для-других-проектов)): номера телефонов (узбекские `+998`/`998` в
любых разбивках, 9-значные местные, российские, другие международные),
e-mail, @упоминания людей и ссылки t.me на людей заменяются заглушками
`[телефон]`, `[почта]`, `[пользователь]`. Ссылки на сообщения
(`t.me/gorets_uzb/12345`), приглашения в чаты и упоминания ботов
остаются. Медиа не скачивается — только тип и имя файла.

**Не хранятся:** служебные сообщения (вступил, вышел, закрепил) и сообщения
ботов.

**Сроки:** сырые сообщения — 90 дней (`GORETS_RETENTION_DAYS`), потом
удаляются в конце ежедневного прогона. Итоги недель (`digests`: отчёт в
Markdown, структурированный JSON, модели, токены, стоимость, когда
доставлен) — бессрочно. Журнал прогонов (`runs`) — бессрочно, он маленький.

Оценка объёма: сообщение занимает в среднем около 300 байт с индексами;
10 тысяч сообщений в месяц × 3 месяца ≈ 10 МБ.

## Установка на VPS по шагам

Нужны: Ubuntu с Python 3.12, `uv`, Postgres (тот же, что у Sayr), доступ
root. Каталог проекта — `/root/Projects/sayr-gorets`.

### 1. База и роль

```bash
sudo -u postgres psql <<'SQL'
CREATE ROLE sayr_gorets LOGIN PASSWORD 'придумайте-пароль';
CREATE DATABASE sayr_gorets OWNER sayr_gorets ENCODING 'UTF8';
SQL
```

### 2. Клонировать и собрать окружение

```bash
mkdir -p /root/Projects && cd /root/Projects
git clone <адрес репозитория> sayr-gorets
cd sayr-gorets
uv sync --frozen --no-dev        # свой venv в .venv, версии из uv.lock
```

### 3. Заполнить `.env`

```bash
cp .env.example .env && chmod 600 .env
```

Обязательно заполнить:

- `GORETS_DATABASE_URL` — пароль роли из шага 1;
- `GORETS_TG_API_ID`, `GORETS_TG_API_HASH` — с <https://my.telegram.org>
  (раздел API development tools), под номером аккаунта-сборщика;
- `GORETS_AUTHOR_HMAC_SECRET` — длинный случайный секрет
  (`openssl rand -hex 32`); потом не менять, иначе `forget-author` не
  найдёт старые записи;
- `GORETS_OWNER` — @username или числовой id владельца, кому слать отчёт;
- `ANTHROPIC_API_KEY` — ключ Claude.

Остальное имеет разумные значения по умолчанию, см. [Настройки](#настройки).

Накатить схему базы:

```bash
.venv/bin/alembic upgrade head
```

### 4. Войти в Telegram

```bash
.venv/bin/gorets login
```

Спросит телефон, код из Telegram и пароль двухфакторной защиты, если он
есть. Строка сессии дописывается в `.env` как `GORETS_TG_SESSION`, если
её там нет; если есть — печатается в stdout, файл не трогается. В журнал
секреты не попадают.

После входа владелец пишет аккаунту-сборщику любое сообщение (см. раздел
про антиспам).

### 5. Загрузить историю

Два пути, можно оба — они друг друга не дублируют (id сообщений совпадают).

**Выгрузка Telegram Desktop** (быстро и без нагрузки на API). В Telegram
Desktop открыть группу → меню ⋮ → «Экспорт истории чата», формат —
«JSON» (Machine-readable JSON), все галочки с медиа снять. Получится
`result.json`, скопировать его на сервер и:

```bash
.venv/bin/gorets import-export /path/to/result.json
```

Файл на сотни мегабайт разбирается потоком. Ветки восстанавливаются по
дереву ответов: в выгрузке нет id ветки, поэтому у ответов на удалённые
сообщения ветка будет неизвестна, а источник пересылок без
`forwarded_from_id` не сохраняется. Если чат не форум — добавьте
`--no-forum`; если в выгрузке нет id чата — `--chat-id`.

**Догрузка через API** (точные ветки и пересылки, но долго и с лимитами):

```bash
.venv/bin/gorets backfill --since 2025-10-01
```

Читает порциями по `GORETS_BACKFILL_BATCH` сообщений (5000) за запуск;
каждый следующий запуск продолжает с места остановки, пока не напишет
«история дочитана». На FloodWait дольше `GORETS_FLOOD_WAIT_MAX` прогон
завершается с ошибкой, прогресс сохранён.

### 6. Включить таймеры

```bash
cp deploy/sayr-gorets-collect.service deploy/sayr-gorets-collect.timer \
   deploy/sayr-gorets-digest.service  deploy/sayr-gorets-digest.timer  /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now sayr-gorets-collect.timer
systemctl enable --now sayr-gorets-digest.timer      # после того как владелец написал сборщику
cp deploy/sayr-gorets-api.service /etc/systemd/system/ && systemctl daemon-reload
systemctl enable --now sayr-gorets-api.service       # если данные нужны другим проектам
cp deploy/sayr-gorets-alert@.service deploy/sayr-gorets-watch.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now sayr-gorets-watch.service     # если нужны вебхуки в реальном времени
```

В шапке каждого unit-файла — как его установить и проверить. Службы
`Type=oneshot`, `NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=strict`;
на запись доступен только `reports/`.

### 7. Проверить

```bash
systemctl list-timers 'sayr-gorets-*'                # когда следующий запуск
systemctl start sayr-gorets-collect.service          # запустить сбор сейчас
journalctl -u sayr-gorets-collect.service -n 50      # журнал сбора
journalctl -u sayr-gorets-digest.service -n 100      # журнал разбора
systemctl --failed                                   # упавшие прогоны
.venv/bin/gorets stats                               # что в базе, последние прогоны
.venv/bin/gorets digest --week 2026-W40 --dry-run    # объём, куски и цена без вызова API
```

### Добавить ещё один чат или канал

Вступить аккаунтом-сборщиком в чат, дописать его username или id в
`GORETS_CHATS` через запятую и запустить сбор (`systemctl start
sayr-gorets-collect.service` или дождаться таймера). Новый чат будет
прочитан с `GORETS_INITIAL_SINCE`, дальше — как остальные. Срок хранения
`GORETS_RETENTION_DAYS` должен покрывать этот период, иначе старые
сообщения удалятся в конце того же прогона.

## Команды

| Команда | Что делает |
|---|---|
| `gorets login` | Интерактивный вход (телефон, код, пароль 2FA) → строка сессии в `.env` |
| `gorets collect` | Новые сообщения по всем чатам из настроек, затем чистка по сроку хранения |
| `gorets backfill --since ГГГГ-ММ-ДД [--limit N]` | Догрузка истории через API порциями с продолжением |
| `gorets import-export result.json [--chat-id N] [--no-forum]` | Импорт выгрузки Telegram Desktop |
| `gorets digest [--week ГГГГ-Wнн] [--dry-run] [--no-send] [--resend]` | Разбор недели (по умолчанию прошлой) и отчёт владельцу; `--dry-run` печатает объём, число кусков и оценку цены, не вызывая API; `--no-send` собирает отчёт без отправки; `--resend` отправляет уже собранный отчёт ещё раз |
| `gorets extract [--extractor имя] [--since ГГГГ-ММ-ДД] [--limit N] [--dry-run]` | Прогнать извлекатели из `gorets.toml` по новым сообщениям фидов |
| `gorets api [--host] [--port]` | HTTP API для других проектов |
| `gorets watch` | Слушатель в реальном времени и вебхуки фидов |
| `gorets alert <unit>` | Сообщить владельцу о сбое службы (вызывает systemd) |
| `gorets mcp` | MCP-сервер для агентов (stdio) |
| `gorets forget-author <tg_user_id>` | Удалить всё, что написал автор (по тому же HMAC) |
| `gorets forget-message <чат> <id>` | Удалить одно сообщение (чат — username или id) |
| `gorets stats` | Что в базе, итоги недель, последние прогоны |

Общий ключ `--env-file ПУТЬ` берёт настройки из другого файла вместо `.env`.
Любая ошибка — ненулевой код выхода.

## Разбор недели

1. **Неделя** — с понедельника 00:00 по воскресенье 23:59 по Ташкенту.
   По умолчанию разбирается прошедшая неделя; `--week 2026-W40` —
   конкретная (нумерация ISO).
2. **Каталог Sayr** берётся из публичного API без ключа
   (`GET …/places?limit=1000`, плюс `&lang=uz` для узбекских названий):
   `slug`, `name`, `category`, `region_name`, `lat`, `lng`, `elevation_m`.
   Ссылка на место в отчёте — `https://sayr.info/p/<slug>`. Без каталога
   разбор не запускается (три попытки, затем ошибка).
3. **Нарезка.** В модель уходит только текст без авторов: ветка, номер и
   дата сообщения, текст, «ответ на» коротко (номер и начало сообщения, на
   которое отвечают). Сообщения без текста попадают в модель, только если
   вложение само по себе говорящее (трек, точка, место, файл, опрос).
   Ветка целиком, если влезает в бюджет; длинные ветки — по частям по
   порядку; короткие — по несколько в одном куске. Токены оцениваются по
   длине текста, без обращения к API.
4. **Куски → Message Batches API** (модель `GORETS_CHUNK_MODEL`). Из
   каждого куска модель возвращает JSON: упоминания мест (как написано и
   `slug` из каталога, если узнаётся), состояние (снег, вода, дорога,
   закрытия, опасности, погода — с датой), объявленные выходы (место,
   даты; без организаторов), вопросы, упоминания Sayr, места не из
   каталога (название, подсказки, где это, координаты, если делились
   точкой). Инструкция и каталог общие для всех кусков и помечены для
   кэширования. Батч опрашивается с паузами до `GORETS_BATCH_WAIT_HOURS`;
   соединение не висит.
5. **Сведение** всех JSON (предварительно объединённых программой по
   `slug`/названию) → отчёт одним вызовом Messages API (модель
   `GORETS_SYNTHESIS_MODEL`). Сколько было людей и сообщений, по веткам и
   по дням — считает программа, не модель.
6. **Отчёт** на русском: 1) места в ходу — топ и что о них говорят;
   2) места, которых нет в каталоге, — кандидаты в черновики; 3) выходы и
   сборы; 4) частые вопросы — чего не хватает в приложении; 5) упоминания
   Sayr; 6) цифры недели. Без имён, ников и телефонов; пересказ, а не
   длинные цитаты. Сохраняется в базу (`digests`: Markdown, JSON, модели,
   токены, стоимость) и в файлы `reports/ГГГГ-Wнн.md` и `.json`.
7. **Доставка** личным сообщением владельцу тем же аккаунтом: до
   `GORETS_DELIVERY_MAX_PARTS` частей по 4096 знаков, иначе — файлом `.md`
   с коротким сопроводительным сообщением.

**Если батч не успел** за отведённое время, прогон завершается с ненулевым
кодом и записью в журнал, а id батча и отпечаток нарезки запоминаются в
`digests`. Повторный `gorets digest --week …` забирает результаты того же
батча, не отправляя новый, — платить второй раз не придётся. Если
отдельные куски не разобрались, отчёт всё равно собирается, а замечания об
этом попадают в раздел «Цифры недели».

**Пересборка готовой недели** (`gorets digest --week …` для недели, которая
уже разобрана) не отправляет батч заново, пока не изменились нарезка,
модель кусков или инструкция: результаты кусков берутся из базы, платится
только сведение. Поменяли инструкцию или модель — батч будет новый.

**Структура JSON отчёта** (`reports/ГГГГ-Wнн.json`, колонка
`digests.report_json`) рассчитана на будущую страницу отчётов в админке
Sayr и заведение черновиков мест без переделки:

```json
{
  "schema_version": 1,
  "week": "2026-W40",
  "period": {"start": "…", "end": "…", "start_date": "28.09.2026", "end_date": "04.10.2026", "timezone": "Asia/Tashkent"},
  "generated_at": "…",
  "headline": "чем жила неделя",
  "places":     [{"name", "slug", "url", "mentions", "summary", "conditions": [{"kind", "text", "date"}]}],
  "new_places": [{"name", "hints", "region", "lat", "lng", "mentions"}],
  "trips":      [{"place", "slug", "url", "dates", "summary"}],
  "questions":  [{"theme", "examples", "count", "app_gap"}],
  "sayr":       {"summary", "items": [{"summary", "sentiment"}]},
  "stats":      {"messages", "messages_with_text", "authors", "topics", "chunks", "by_day", "media", "tracks", "points", "top_topics"},
  "models":     {"chunk", "synthesis"},
  "usage":      {"input_tokens", "output_tokens", "cache_read_tokens", "cost_usd"},
  "notes":      ["замечания прогона"]
}
```

`slug` в отчёте — только из каталога (несуществующие модель назвать может,
программа их обнуляет). `kind` состояния: `snow`, `water`, `road`,
`closure`, `danger`, `weather`, `other`.

## Фиды, извлекатели и API для других проектов

Сервис умеет отдавать собранное другим проектам Sayr на том же VPS,
например агрегатору туров. Три понятия:

**Фид** — именованный выбор сообщений: чат плюс ветки (названия или id).
Описывается в [`gorets.toml`](gorets.toml), файл хранится в репозитории.
У фида с `keep_contacts = true` текст сообщений хранится как есть: в
коммерческих ветках (афиши, объявления) телефон и ник организатора — часть
предложения, а не личные данные. Во всех остальных ветках очистка работает
как раньше.

```toml
[feeds.afisha]
chat = "gorets_uzb"
topics = ["АФИША ПОХОДОВ"]   # начало названия ветки, регистр не важен
keep_contacts = true
```

Сейчас описаны ветки обоих форумов: афиша, поиск попутчиков, диспетчерская,
описания маршрутов, погода и чат в «ГОРЕЦ»; поиск попутчиков,
диспетчерская, отчёты и трекохранилище в «Горняшке». Извлекатели:
`afisha_tour` (туры из афиш), `companion_request` (поиск попутчиков в обоих
чатах), `trail_condition` (состояние троп из диспетчерских, чата и отчётов).

**Извлекатель** — инструкция модели и JSON-схема, привязанные к фиду. Раз в
день (вторым шагом службы сбора) каждый новый текст фида уходит в Message
Batches API одним запросом, модель решает, по теме ли сообщение
(`relevant`), и возвращает структуру по схеме. Результат хранится в
таблице `extractions` бессрочно, даже после удаления сырого сообщения по
сроку, повторно сообщение не разбирается. Извлекатель может
работать по нескольким фидам сразу (`feeds = [...]`). Новый вид извлечения
— ещё одна секция в `gorets.toml`, без правки кода.

```bash
.venv/bin/gorets extract --dry-run            # сколько сообщений ждёт и оценка цены
.venv/bin/gorets extract --extractor afisha_tour --since 2026-01-01
```

**HTTP API** — FastAPI, только чтение, слушает `127.0.0.1:8765`, токен
`GORETS_API_TOKEN` в заголовке `Authorization: Bearer …` или
`X-API-Token`. Служба `deploy/sayr-gorets-api.service`.

| Запрос | Что отдаёт |
|---|---|
| `GET /health` | без токена: живость, свежесть сбора, последние прогоны по видам |
| `GET /feeds` | описанные фиды |
| `GET /feeds/{name}/messages?after=&since=&until=&q=&dedupe=&limit=` | сообщения фида по возрастанию `msg_id`; `after` — курсор; `dedupe=true` пропускает повторы того же текста (и из других чатов) |
| `GET /search?q=&feed=&since=&until=&limit=` | полнотекстовый поиск с русской морфологией; синтаксис websearch: слова, `"фраза"`, `-минус` |
| `GET /messages/{chat}/{msg_id}` | одно сообщение |
| `GET /messages/{chat}/{msg_id}/duplicates` | тот же текст в других чатах и ветках |
| `GET /extractors` | извлекатели, их схемы и счётчики |
| `GET /extractions/{name}?after=&since=&until=&status=&limit=` | результаты извлекателя; `after` — курсор по `id`, `status` = `ok` (по умолчанию), `skipped`, `error`, `all` |
| `GET /events?from=&to=&kind=&since=` | календарь выходов из афиш и попутчиков; `kind` = `tour` или `companions`; дубли из разных чатов схлопнуты |
| `GET /events.ics?from=&to=&kind=` | то же в iCalendar — можно подписаться календарём |
| `GET /places/top?since=&limit=` | места каталога Sayr по числу упоминаний |
| `GET /places/{slug}/mentions?since=&limit=` | всё извлечённое о месте: упоминания, состояние троп, туры, вопросы |
| `GET /questions/themes?since=` | о чём спрашивают, по темам со счётчиками, примерами и местами — бэклог приложения |
| `GET /stats/authors?feed=&since=&limit=` | самые активные и самые «отвечаемые» авторы фида (только хеши) |
| `GET /digests`, `GET /digests/{week}?format=json\|md` | итоги недель |

Ответы списков: `{"items": [...], "next_cursor": …, "has_more": true}`.
Потребитель запоминает `next_cursor` и в следующий раз передаёт его в
`after` — так ничего не теряется и не дублируется. У каждого сообщения и
извлечения есть `link` на оригинал в Telegram.

Пример потребителя на FastAPI с `httpx`:

```python
import httpx

GORETS = httpx.Client(base_url="http://127.0.0.1:8765",
                      headers={"Authorization": f"Bearer {GORETS_API_TOKEN}"})

def new_tours(cursor: int | None) -> tuple[list[dict], int | None]:
    page = GORETS.get("/extractions/afisha_tour", params={"after": cursor, "limit": 200}).json()
    return page["items"], page["next_cursor"]   # item["data"] — тур по схеме, item["link"] — пост
```

### Привязка мест к каталогу

У извлекателя можно указать `link_places = ["place"]` или
`["places[].name"]`: после извлечения название места сопоставляется с
каталогом Sayr без обращения к модели (точное название по-русски или
по-узбекски, затем «ядро» без слов «гора», «озеро», «перевал», затем
вхождение) и в данные добавляется `place_slug` (или `slug` у элемента
списка). На этом держатся `/places/top`, `/places/{slug}/mentions`, слаги в
событиях и вопросах. Если каталог недоступен, извлечение всё равно
выполняется, slug остаётся пустым.

### Вебхуки и слушатель в реальном времени

Ежедневный сбор запаздывает на сутки; для афиш это терпимо, для «перевал
закрыт» — нет. Служба `deploy/sayr-gorets-watch.service` (`gorets watch`)
держит соединение с Telegram, пишет новые и отредактированные сообщения в
базу сразу и шлёт `POST` на `webhook_url` каждого фида, в который попало
сообщение:

```toml
[feeds.afisha]
chat = "gorets_uzb"
topics = ["АФИША ПОХОДОВ"]
keep_contacts = true
webhook_url = "http://127.0.0.1:8000/hooks/gorets"
webhook_secret = "длинный-секрет"
```

Тело — `{"event": "message" | "message_edited", "feed": "afisha",
"message": {…как в API…}}`, заголовки `X-Gorets-Event`, `X-Gorets-Feed`
и `X-Gorets-Signature: sha256=<HMAC-SHA256 тела по webhook_secret>`.
Проверка на стороне потребителя — `gorets.webhooks.verify_signature`
или те же три строки на любом языке. Три попытки с паузой, неудача
пишется в журнал и не останавливает слушатель. Сбор по таймеру остаётся и
догоняет пропущенное, пока слушатель не работал.

### Оповещения о сбоях

Во всех unit-файлах стоит `OnFailure=sayr-gorets-alert@%n.service`:
упавшая служба запускает `gorets alert <unit>`, и владелец получает в
Telegram сообщение с последней ошибкой из журнала прогонов и подсказкой
`journalctl -u …`. Проверить: `systemctl start sayr-gorets-alert@test.service`.

### MCP-сервер для агентов

`gorets mcp` поднимает MCP-сервер (stdio) с теми же данными: `list_feeds`,
`feed_messages`, `search_messages`, `list_extractors`, `extractions`,
`events`, `places_top`, `place_mentions`, `question_themes`, `digest`.
Нужна дополнительная зависимость: `uv sync --extra mcp` (на сервере
`uv sync --frozen --no-dev --extra mcp`). Пример для Claude Code на том же
сервере:

```json
{"mcpServers": {"gorets": {"command": "/root/Projects/sayr-gorets/.venv/bin/gorets", "args": ["mcp"]}}}
```

Токен не нужен: сервер ходит в базу напрямую, доступ определяется тем,
кто может запустить процесс.

## Цена в месяц

Формула для недели (цены за миллион токенов; батч вдвое дешевле):

```
куски    = 0.5 × [ (T_сообщений + N_кусков × T_инструкции) × Вход(Haiku) + N_кусков × T_ответа × Выход(Haiku) ]
сведение = (N_кусков × T_ответа + 3 000) × Вход(Sonnet) + 6 000 × Выход(Sonnet)
```

где `T_сообщений` — токены текста недели, `T_инструкции` ≈ 20 000 (инструкция
плюс каталог на тысячу мест; при попадании в кэш — десятая часть цены),
`T_ответа` ≈ 1 500 на кусок. Цены (Haiku 4.5: $1 вход / $5 выход; Sonnet 5.5:
$2 / $10) зашиты в `digest/pricing.py`.

Пример: неделя с 2 500 сообщениями с текстом по 150 знаков ≈ 150 000
токенов ≈ 13 кусков по 12 000.

| Ступень | Токены | Стоимость |
|---|---|---|
| Куски, вход (Haiku, батч) | 150 000 + 13 × 20 000 = 410 000 | $0.21 |
| Куски, выход (Haiku, батч) | 13 × 1 500 = 19 500 | $0.05 |
| Сведение, вход (Sonnet) | 19 500 + 3 000 = 22 500 | $0.05 |
| Сведение, выход (Sonnet) | 6 000 | $0.06 |
| **Неделя** | | **≈ $0.37** |
| **Месяц** (4,3 недели) | | **≈ $1.60** |

Втрое более шумная неделя — около $1, то есть до $5 в месяц. Извлекатели
добавляют свои копейки: одно сообщение фида — один запрос Haiku в батче,
около $0.001; при 300 сообщениях в день по трём извлекателям на общий чат
это ещё $5–10 в месяц. `gorets extract --dry-run` показывает очередь и
оценку, лишние извлекатели выключаются удалением секции из `gorets.toml`. Точную оценку
для конкретной недели даёт `gorets digest --week … --dry-run`; фактическая
стоимость каждого разбора хранится в `digests.cost_usd` и видна в
`gorets stats`. Telegram и каталог Sayr бесплатны.

```bash
/root/Projects/sayr-gorets/deploy/update.sh            # до origin/main
/root/Projects/sayr-gorets/deploy/update.sh v0.2.0     # до тега или коммита
```

Скрипт делает `git pull` (или checkout указанной версии), `uv sync --frozen
--no-dev`, `alembic upgrade head` и копирует изменившиеся unit-файлы в
`/etc/systemd/system` с `daemon-reload`. Таймеры трогать не нужно: следующий

Откат кода — тем же скриптом с прежним тегом или коммитом. Откат схемы —

данными, поэтому перед ним — `pg_dump sayr_gorets`.

## Удаление по просьбе

Sayr обещает удалять данные участников по первой просьбе. Авторов в базе
нет — только HMAC, но тот же HMAC считается из id пользователя Telegram:

```bash
.venv/bin/gorets forget-author 123456789          # всё, что написал пользователь с этим id
.venv/bin/gorets forget-message gorets_uzb 118000 # одно сообщение (чат — username или id)
```

Команды печатают, сколько строк удалено. Удалённое не вернётся следующим
сбором: сбор читает только id больше последнего сохранённого, а `backfill`
— только незавершённые догрузки. Итоги недель содержат пересказ без имён и
не меняются.

Id пользователя можно узнать, например, у бота @userinfobot или из ссылки
`tg://user?id=…`; сам сборщик id нигде не хранит.

## Если что-то пошло не так

- **`systemctl --failed` показывает `sayr-gorets-collect`** — смотрите
  `journalctl -u sayr-gorets-collect.service -n 100`. Частые причины:
  недействительная сессия (`gorets login` заново), долгий FloodWait
  (прогресс сохранён, завтра продолжится), недоступный Postgres.
- **`sayr-gorets-digest` упал с «батч не завершился»** — запустите
  `gorets digest --week ГГГГ-Wнн` позже: результаты батча заберутся без
  повторной отправки. Срок хранения результатов батча у Anthropic — 29 дней.
- **Отчёт собран, но не отправлен** — ошибка доставки печатается в журнал,
  отчёт лежит в `reports/` и в базе. Проверьте `GORETS_OWNER` и что
  владелец писал аккаунту-сборщику, затем
  `gorets digest --week ГГГГ-Wнн --resend` — отправит сохранённый отчёт без
  обращения к Claude.
- **Модель не принимает схему JSON** (все куски с ошибкой `invalid_request`)
  — поставьте `GORETS_STRUCTURED_OUTPUT=false`.
- **Telegram ограничил аккаунт** — см. раздел про выбор аккаунта; сбор
  переживёт паузу в несколько дней, догонит с последнего id.
